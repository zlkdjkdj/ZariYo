- **User 엔티티 확장**:

  - `UserStatus` Enum: `ACTIVE`, `SUSPENDED`, `INACTIVE`
  - `status`, `createdAt` 필드 및 도메인 변경 메서드(`updateRole`, `updateStatus`) 추가.
- **Admin User API 구축 (`AdminUserController.java` / `AdminUserService.java`)**:
  - `GET /api/v1/admin/users`: 키워드 검색(이메일/이름), 역할별/상태별 필터링 회원 목록 조회

  - `PATCH /api/v1/admin/users/{userId}/role`: 회원 권한 변경 (OWNER ↔ ADMIN ↔ CUSTOMER)
  - `PATCH /api/v1/admin/users/{userId}/status`: 회원 계정 상태 변경 (ACTIVE ↔ SUSPENDED)
  - `DELETE /api/v1/admin/users/{userId}`: 회원 계정 영구 삭제
- **초기 데이터 설정 (`DataInitializer.java`)**:
  - `CommandLineRunner`를 통해 시스템 최고 관리자(`admin@zariyo.com`), 사장님 샘플 계정, 손님 계정들을 서버 기동 시 자동 구성.

## 5. Refresh Token 기반 무중단 자동 토큰 재발급(Silent Refreshing) 파이프라인
- **백엔드 구축**:
  - `UserDto.RefreshTokenRequest`: 토큰 재발급 요청 DTO
  - `AuthService.refresh()`: Refresh Token 서명 및 만료 시간 검증 ➔ `userId` 식별 ➔ 정지 계정 체크 ➔ 새 Access/Refresh 토큰 발급
  - `AuthController.java`: `POST /api/v1/auth/refresh` API 엔드포인트 개설
- **프론트엔드 구축**:
  - `authApi.refresh()`: 토큰 재발급 클라이언트 API 추가
  - `client.ts`: Response Interceptor에서 401 에러 감지 시 유저 몰래 `zariyo_refresh_token`을 사용해 새 토큰을 받아오고, 원래 실패했던 이전 요청을 0.01초 만에 자동 재시도하는 Silent Refreshing 구현
  - `LoginPage.tsx`: 로그인 시 `zariyo_refresh_token` 저장 추가

## 7. 실무에서의 로그인 관리 방식 (Enterprise Authentication Pattern)
1. **토큰 보안 보관**:
   - `Access Token` (15분~1시간): JS 메모리 / React State에 보관
   - `Refresh Token` (7일~30일): JavaScript 접근이 불가능한 **`HTTP-Only + Secure Cookie`**에 저장하여 XSS 공격 방어
2. **백엔드 Redis 세션 관리**:
   - `Refresh Token`을 In-Memory DB인 Redis에 저장하여 강제 로그아웃/계정 정지 시 토큰을 블랙리스트 처리 또는 삭제
3. **RTR (Refresh Token Rotation)**:
   - Access Token 재발급 시 Refresh Token도 1회용으로 함께 갱신하여 토큰 탈취 여부 감지

## 8. 카카오 소셜 로그인 (Kakao OAuth 2.0) 연동 절차
1. **Kakao Developers 개발자 설정**: REST API 키 발급, Web 도메인(`http://localhost:5173`) 및 Redirect URI (`http://localhost:5173/auth/kakao/callback`) 등록, 동의항목(닉네임, 이메일) 설정
2. **프론트엔드**: 카카오 인가 코드 요청 링크 이동 ➔ 콜백 페이지에서 `code` 파라미터 추출 ➔ 백엔드 `POST /api/v1/auth/kakao` 전송
3. **백엔드**: `code`로 Kakao Access Token 교환 ➔ Kakao 유저 정보 조회 ➔ DB 유저 조회/자동 회원가입 ➔ ZariYo 자체 **JWT Access/Refresh Token 세트** 반환

## 10. AI 코드 에이전트의 소극적/보수적 코드 수정 동작 원리 분석
- **원인 분석**:
  1. **안전성 지향 가이드라인 (Safety & Ponytail Mode)**: 기존 코드가 동작 불능이 되는 통째로 덮어쓰기를 지양하고, `replace_file_content`로 1~2개 파일씩 안정성이 입증된 증분 편집(Small Incremental Edits)을 지향합니다.
  2. **광범위 요청의 세분화**: "전체 페이지 디자인 변경"처럼 광범위한 요청 시 한 번의 턴에서 빌드 파괴를 막기 위해 주요 핵심 3~4개 페이지(Landing, Header, Canvas, Kiosk)를 선별 수정합니다.
  3. **번들 검증 의무 (Verification Safety)**: 코드 수정 후 항상 `pnpm run build`로 컴파일 무결성을 입증해야 하므로, 빌드가 깨지지 않는 단위로 신중하게 진행합니다.
- **적극적 개편 유도 방법**:
  - "파일 전체를 완전히 새로 작성해도 좋으니 전면 재작성해줘"라고 명시하거나, specific 파일 대상을 직접 지정하면 대담한 개편이 단행됩니다.
